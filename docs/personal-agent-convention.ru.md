# Конвенция работы с ИТС для личных агентов

Эта конвенция применяется к личным проектам Дениса, Codex, Claude Code и другим
подключённым агентам. Она не предназначена для процессов команды.

## Язык

Названия задач, описания, комментарии и статусы в ИТС пишутся на русском языке.
Исключение — технические идентификаторы, названия сервисов, команды и фрагменты кода.

## Учётные записи и история действий

- Денис работает под своей учётной записью.
- Каждый агент, который создаёт задачи или оставляет комментарии, имеет отдельный
  профиль агента и отдельный API-ключ.
- Ключ агента используется только в MCP-настройке этого агента.
- Задачи и комментарии создаются от имени фактического исполнителя. Не следует
  использовать личный ключ Дениса для действий агента.
- Ключи не сохраняются в git, документации или ИТС. Они хранятся в локальном
  защищённом хранилище соответствующего агента.

## Проекты и инициативы

- Для каждого нового направления создаётся отдельный проект ИТС с коротким ключом.
- Крупная цель, состоящая из нескольких задач, оформляется инициативой.
- Задача относится к инициативе, если она вносит прямой вклад в её результат.
- Небольшие разовые работы можно вести без инициативы.

### Инициативы

Инициатива описывает крупный результат, который требует нескольких задач и
может включать несколько проектов. Она не дублирует список задач.

- Инициатива получает понятное название результата, владельца, приоритет и
  целевую дату, если она известна.
- В описании фиксируются ожидаемый результат, границы работы и критерий, по
  которому можно признать инициативу завершённой.
- Агент связывает с инициативой только задачи, которые непосредственно ведут к
  её результату.
- Новую инициативу создают для большой самостоятельной цели. Для нескольких
  шагов внутри одной задачи или для разовой работы инициатива не нужна.
- При существенном изменении цели, срока или риска агент оставляет комментарий
  в инициативе и обновляет связанные задачи.
- Инициатива завершается после выполнения критерия результата, а не только
  потому, что у всех связанных задач закрыт статус.

## Как оформлять задачу

Каждая задача содержит:

1. Короткое название в форме действия и ожидаемого результата.
2. Описание: что нужно сделать и зачем это нужно.
3. Критерий готовности, если результат можно проверить.
4. Ссылки на зависимые задачи, сервисы или документы, если они есть.
5. Ответственного: Дениса или конкретного агента.
6. Реалистичный приоритет: высокий только для работ, которые блокируют другие
   задачи, влияют на доступность или создают риск потери данных.

Не создавать отдельную задачу ради заметки. Контекст, уточнения и результаты
работы добавляются комментариями к существующей задаче.

Если задача создаётся в инфраструктурном проекте и относится к самому ИТС, её
название начинается с префикса `[ИТС]`.

## Чеклисты

Чеклист ведёт короткие действия, необходимые для выполнения одной задачи. У
всех пунктов общий исполнитель, общий срок и один результат задачи.

Чеклист используют, если одновременно верны все условия:

- пункт занимает короткое время и не требует отдельного обсуждения;
- пункт не нужно назначать другому исполнителю;
- у пункта нет собственного дедлайна, приоритета или статуса;
- результат пункта не нужен как самостоятельная единица в истории и отчётах.

Обычно в чеклисте от двух до семи пунктов. Каждый пункт формулируется как
действие или проверка: «Настроить…», «Проверить…», «Получить подтверждение…».
Агент отмечает пункт только после фактического выполнения или проверки.

Пункт, который должен выполнить Денис, начинается с `Денис:`. Если его нужно
отслеживать отдельно, назначить или привязать к сроку, это не пункт чеклиста, а
задача.

## Подзадачи и зависимости

Подзадача — самостоятельная задача внутри более крупного результата. В отличие
от пункта чеклиста, у неё могут быть собственные исполнитель, дедлайн, статус и
комментарии.

- Подзадачу создают, если часть работы имеет отдельный готовый результат, может
  выполняться независимо или требует отдельного отслеживания.
- Подзадача обязательна, если у части работы другой исполнитель, собственный
  дедлайн, приоритет, риск, блокер или зависимость.
- Подзадача подходит для результата, который Денису нужно отдельно принять,
  проверить или увидеть в истории.
- Короткие технические шаги одного исполнителя остаются пунктами чеклиста.
- Не создавать подзадачи для этапов «начать», «сделать», «закончить» и других
  формальных состояний. Они отражаются статусом родительской задачи.
- Родительская задача описывает общий результат; подзадачи описывают части,
  которые вместе к нему приводят. Родительская задача не закрывается, пока не
  завершены необходимые подзадачи и не проверен общий критерий готовности.
- Если одна задача действительно не может быть завершена до другой, агент
  связывает их зависимостью «блокирует» или «заблокирована». Связь «относится к»
  применяется для полезного контекста без блокировки.
- Дубликаты не ведутся параллельно: агент связывает их как дубликаты и предлагает
  Денису, какую из задач оставить основной, если это не очевидно.
- После снятия блокера агент обновляет статус зависимой задачи и оставляет
  комментарий только при необходимости объяснить следующий шаг.

### Быстрый выбор

| Ситуация | Использовать |
| --- | --- |
| Проверить три пункта перед передачей одного результата | Чеклист |
| Денис должен выдать доступ или принять отдельный результат | Подзадача |
| Работу можно поручить другому агенту | Подзадача |
| Шаг имеет собственный срок, приоритет или блокер | Подзадача |
| Нужна только личная последовательность коротких действий | Чеклист |

## Заметки

Заметка — короткий стикер с текущим контекстом проекта. Она не заменяет
документ, задачу, комментарий или инициативу.

- Заметки содержат только краткую полезную информацию: ссылки, ограничения,
  контакты сервисов, текущие договорённости или известные риски.
- Заметка пишется на русском языке и остаётся короткой. Инструкция из нескольких
  шагов, описание архитектуры или журнал работы хранятся в документации проекта.
- В заметках не хранятся секреты, API-ключи, пароли, cookies или персональные
  данные.
- Если из заметки следует конкретное действие, агент создаёт или обновляет
  задачу.
- Агент обновляет или удаляет заметку, когда указанный в ней оперативный контекст
  перестал быть актуальным.

## Статусы и ответственность

- Новые согласованные работы создаются в Backlog.
- Исполнитель переводит задачу в работу, когда действительно начинает её выполнять.
- Выполненную агентом работу агент сопровождает комментарием: что сделано, что
  проверено, какие действия остаются Денису.
- Задача считается завершённой после проверки результата или явного подтверждения
  Дениса, если проверка требует его доступа или решения.
- Если задача ждёт решения Дениса, агент назначает её Денису и формулирует в
  комментарии конкретный вопрос или нужное действие.

## Регламент работы агента

### Начало сессии

В начале каждой сессии агент просматривает доступные ему задачи ИТС:

- задачи, назначенные ему;
- задачи с дедлайном сегодня и просроченные задачи;
- задачи, где есть новое упоминание, комментарий или запрос действия;
- задачи в работе, которые агент начал в предыдущих сессиях.

Этот просмотр не означает, что агент начинает все найденные задачи. Он нужен,
чтобы учесть срочные обязательства и не потерять уже начатую работу.

### Создание и назначение задач

- Агент может создавать задачи для себя и для Дениса в рамках согласованной
  инициативы или прямого поручения.
- Агент назначает задачу Денису, когда для следующего шага нужны решение,
  доступ, оплата, действие в интерфейсе или проверка Дениса.
- Задача, назначенная Денису, содержит конкретный следующий шаг и достаточный
  контекст для его выполнения.
- Агент назначает задачу себе, когда может выполнить её самостоятельно и она
  достаточно велика, чтобы её результат требовал отслеживания.
- Новые задачи не дублируют существующие. Перед созданием агент ищет похожую
  открытую задачу в том же проекте.

### Обновление статусов

Агент обновляет статус в момент фактического изменения состояния:

- переводит задачу из Backlog в работу непосредственно перед началом;
- отмечает ожидание или блокер, когда без действия Дениса, внешнего сервиса или
  другой задачи продолжать нельзя;
- переводит задачу к проверке или завершению, когда результат готов;
- не меняет статус только для создания видимости активности.

При блокере агент добавляет комментарий: что заблокировано, почему, кто может
устранить причину и какой следующий шаг нужен.

### Дедлайны

- Агент может устанавливать и изменять дедлайны.
- Дедлайн ставится, когда известна конкретная дата: внешний срок, согласованное
  окно работ, продление сервиса, релиз или обязательство перед Денисом.
- Агент не придумывает дату ради заполнения поля. Если срок является оценкой,
  это прямо указывается в описании или комментарии.
- При изменении важного дедлайна агент оставляет комментарий с причиной и новой
  датой.

### Приоритет и объём работы

- Высокий приоритет используется для задач, которые блокируют работу, влияют на
  доступность, безопасность, деньги или риск потери данных.
- Обычная работа получает средний или низкий приоритет.
- Если задача стала заметно шире исходной цели, агент создаёт отдельную задачу
  или просит Дениса подтвердить расширение объёма.

### Завершение и передача результатов

- Перед завершением агент проверяет критерий готовности, если он задан.
- Агент оставляет итоговый комментарий: что сделано, как это проверено и что
  нужно знать Денису.
- Если результат должен проверить Денис, агент не закрывает задачу. Он назначает
  её Денису или переводит в соответствующий статус ожидания и указывает точный
  способ проверки.
- В конце сессии агент обновляет задачи, состояние которых изменилось в этой
  сессии. Он не обязан комментировать задачи без изменений.

## Комментарии

Комментарий добавляется, когда он меняет состояние работы: есть результат,
блокер, решение, проверка или запрос действия. В комментарии указываются факты,
ссылки на результаты и следующий шаг. Не добавляются промежуточные сообщения без
полезной информации.

## Работа агентов

- Агент не начинает назначенную задачу автоматически только из-за назначения.
  Он начинает её по прямому указанию Дениса или в рамках явно согласованной
  последовательности работ.
- Перед потенциально рискованными действиями агент обсуждает подход и получает
  согласие Дениса.
- Агент не закрывает задачу, если итог требует решения, доступа или проверки
  Дениса; вместо этого он оставляет комментарий с результатом и следующим шагом.
- При добавлении нового агента создаётся отдельный профиль и API-ключ, затем
  подключение проверяется через MCP до начала работы.

## Настройки проекта и автоматизация

- Метки, пользовательские поля и новые типы задач добавляются только когда они
  нужны для повторяющейся классификации или отчётности, а не для одной задачи.
- Циклы используются только после явного согласования регулярного ритма работы,
  например недельного или двухнедельного. В остальных случаях достаточно
  приоритета и дедлайна задачи.
- Представления и дашборды создаются для повторяющегося обзора: просроченные
  задачи, работа конкретного агента или ход инициативы. Разовый вопрос не требует
  нового представления или дашборда.
- Вложения добавляются, когда файл нужен для выполнения или проверки задачи. В
  ИТС не загружаются секреты и долгосрочная документация.
- Автоматические действия, webhooks, расписания запусков и триггеры по упоминанию
  или назначению не включаются без отдельного согласования Дениса. Они могут
  запускать агента или внешнее действие без активной сессии.
- Инструменты из каталога Tools подключаются только под конкретный сценарий,
  после проверки требуемых прав, стоимости и объёма доступа к внешнему сервису.

## Штатные Telegram-уведомления

Telegram используется для штатных событий ИТС и не требует внутреннего агента
или модели. Доставка выполняется существующим worker ИТС.

- Бот настраивается один раз на уровне всего экземпляра ИТС. Токен вводится
  владельцем только через настройки ИТС и хранится там в зашифрованном виде.
- Денис подключает свой Telegram-аккаунт к профилю ИТС один раз. Этот чат затем
  используется во всех проектах, где включены Telegram-уведомления.
- При создании нового проекта владелец включает Telegram в настройках уведомлений
  проекта и включает для Дениса события: назначение задачи, упоминание,
  комментарий в отслеживаемой задаче и изменение статуса отслеживаемой задачи.
- Уведомление не заменяет работу с задачей. Агент всё равно обновляет статус,
  комментарий и назначение по правилам этой конвенции.
- Токен бота, идентификаторы чатов и другие секреты не сохраняются в репозитории,
  заметках, задачах или комментариях.
- Ежедневные сводки по дедлайнам не относятся к штатным событиям. Они требуют
  отдельной реализации и согласования.

## Подключение нового проекта

1. Создать проект и определить его короткий ключ.
2. При необходимости создать инициативу для крупной цели.
3. Включить MCP для проекта.
4. Поручить работающему агенту начальную настройку по инструкции ниже.
5. Подключить ключ только к соответствующему агенту.
6. Проверить, что действия агента в истории ИТС отображаются от его имени.
7. Создать стартовые задачи на русском языке и назначить ответственных.

## Подключение агента к ИТС через MCP

Новый проект подключает уже работающий агент с административным доступом к ИТС.
Он создаёт профиль нового агента и выпускает для него отдельный API-ключ.
Начальная настройка выполняется от имени Дениса, а дальнейшая работа — от имени
созданного агента.

### Что делает Денис в ИТС

1. Создать новый проект и определить его короткий ключ.
2. Включить MCP в настройках проекта.
3. Передать агенту эту конвенцию и поручить начальную настройку.

### Что делает агент при начальной настройке

1. В нужном проекте создать внешнего агента с понятным именем, например
   `Codex` или `Claude Code`.
2. Выдать ему роль, достаточную для его задач. По умолчанию — Member.
3. Не включать автоматический запуск при назначении или упоминании, пока это
   отдельно не согласовано.
4. Выпустить отдельный API-ключ для этого агента.
5. Попросить Дениса безопасно сохранить ключ в локальном файле на машине
   целевого агента. Значение ключа не отправляется в чат.

Если у агента нет административного доступа к ИТС, он сообщает об этом. Тогда
Денис создаёт профиль и ключ вручную в интерфейсе ИТС, после чего агент
продолжает настройку.

Для текущего сервиса используется адрес MCP:

```text
https://api-its.evolveronline.uk/mcp
```

Этот адрес обходится без Cloudflare Access только для пути `/mcp`. Сам сервер
ИТС требует API-ключ, поэтому ключ нужен для каждого запроса.

### Codex

1. Сохранить ключ в `~/.codex/secrets/itsaplan-mcp.env` с правами `600`:

```text
ITSAPLAN_CODEX_API_KEY=
```

2. В `~/.codex/config.toml` создать или обновить сервер `itsaplan`. Значение
ключа копируется из локального защищённого файла. Оно хранится только в локальной
конфигурации Codex и не попадает в git или документацию:

```toml
[mcp_servers.itsaplan]
url = "https://api-its.evolveronline.uk/mcp"
http_headers = { Authorization = "Bearer <локальный API-ключ агента>" }
```

3. Ограничить права файла конфигурации: `chmod 600 ~/.codex/config.toml`.
4. Перезапустить Codex и проверить подключение командой `codex mcp get itsaplan`.

### Claude Code

Команда сохраняет ключ в локальной пользовательской конфигурации Claude Code.
Не вставлять реальный ключ в общие инструкции, репозиторий или чат.

```bash
claude mcp add --scope user --transport http itsaplan \
  https://api-its.evolveronline.uk/mcp \
  --header "Authorization: Bearer <локальный API-ключ агента>"
```

После подключения проверить состояние командой:

```bash
claude mcp list
```

### Проверка авторства

После перезапуска агент делает безопасный запрос чтения, например получает
список доступных проектов. Затем Денис открывает историю ИТС и проверяет, что
действие отражается от имени этого агента. Только после такой проверки агент
создаёт или изменяет рабочие задачи.

### Отзыв доступа

Если агент больше не используется, его API-ключ отзывается в ИТС. Затем
локальная запись ключа удаляется из защищённого хранилища и из MCP-конфига
соответствующего агента.
